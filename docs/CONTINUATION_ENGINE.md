# Continuation Engine

## G7 product views

The four primary entries are Match first, Inspiration first, Upgrade and Harmony Wish ([D13](../DECISIONS.md#d13-g7-四入口与双推荐视图)). Match retains the four original intent subviews and the exact Unified policy. Inspiration presents one cross-intent list with Stable/Rich/Bold route labels and separate source-channel labels. A source phrase's editorial review never becomes a cross-phrase seam review.

The worker's explicit `prepareBothViews` request computes an Exact bank using the saved Match intent and a neutral G6 inspiration bank. Existing worker clients without that flag keep their original contract. Both results are immutable until input/preferences actually change. Runtime primary navigation selects the bank, keeps the input and current audition, and does not request recomputation. The selected Match subfunction remains a ranking preference; changing it retains the original scoring semantics. Navigation-only bank updates preserve the other entry's selection, page and pinned music object. Playback resolves representatives in both banks and keeps the active source identity when a common music ID has different explanations.

`mixedInspirationOrder` produces group/index references to the original candidates off the UI thread. It retains all legal music identities, uses soft 20/50/30 direction and 25/40/35 Exact/context/seam exposure targets, and compares raw scores only within a channel. Quality, first harmony, bass contour, family, destination, use and actual subsequent route distinguish candidates. A single-chord creative fragment stays accessible but receives lower homepage priority. Exact source type no longer implies Stable: the inspiration-only direction projection checks the realized harmony, including ordinary minor dominant usage. Match scores, qualification, actual chords and source evidence are untouched.

The view accepts only its current request generation. A fixed-size native UI test uses two real worker results, delays the first past the second request, rejects it through the production view gate, and accepts the current result while pumping Win32 UI events. This is native UI evidence, not DAW or human audition acceptance. Session5/Snapshot3 remain unchanged; navigation is runtime state and G6 snapshots without seam metadata remain labeled as frozen performance. Five music materials and their pending human-review status live in [G7 review](G7_FOUR_ENTRY_REVIEW.md).

## G6 / Harmony Engine V2

V2 adds an opt-in core request (`inspirationPriority`). G6 initially exposed it as a lightweight control for Develop/Loop/Color; G7 uses the product views above. Resolve qualification remains Unified-only. Wish's random sampler and input qualification do not opt into V2. The UI preference is instance-owned and intentionally omitted from Session5 serialization.

`CandidateIndex` precomputes internal source anchors plus diatonic terminal-class entry records for admitted V7 editorial phrases. These are source-relative records, not all pairs of catalogue phrases. The immutable source template supplies its complete ID, exact realization, source coordinate and authored rhythm. Internal anchors retrieve an exact contiguous complete input, tail three, or tail two; explicit quality, bass and performed tone requirements remain binding. No DP similarity cutoff is reused for the creative channel.

Phrase entries have a reviewed source phrase but an **algorithm-assessed seam**. A source's editorial review never certifies the new seam. Actual bass, extended pitch masks, shared tones and nearest tone movement must pass the boundary gate. Major/minor relative centers are recorded as dual interpretations. New target centers are restricted to query-supported or neighboring circle-of-fifths centers; a modulation additionally requires a shared diatonic pivot including its extensions and a destination V-I within the authored phrase. Source-coordinate center, input interpretation and destination are distinct runtime fields. The pool currently has no independently editorial-reviewed seam records.

Creative quality is conjunctive: boundary, context, center logic, source confidence, independent phrase value, realizability and hard melody constraints must each pass. Novelty and complexity cannot repair a failed gate. Existing exact scores are preserved; a creative raw score is never compared with an exact raw score. Comparable quality bands precede soft 20/50/30 Stable/Rich/Bold deficits and diversity in first harmony, bass contour, family, center, use, color and guide-tone contour. Guide-tone contour is a ranking affordance, not evidence of a sourced melody. Full music identity still includes exact bass, masks, rhythm and constraints. Every qualified retained route remains in pagination. No creative candidate enters Resolve.

New playback, MIDI and snapshots consume the **actual input plus the frozen source suffix**; exact continuation retains the established full-source projection below. A local suffix has direct *catalogue* continuity, which may be an editorial original construction; it does not imply a commercial work transcription. A phrase transition never receives a fabricated matcher trace. Snapshot3 freezes actual performed data and the suffix source ID; V2's channel/center/seam metadata is not serialized. A restored `g6:` snapshot is labeled as frozen music and does not claim restored seam provenance. A future optional metadata extension needs a separately approved persistence decision.

The scoped three-input evidence and music verdict live in [G6 review](G6_ENGINE_V2_REVIEW.md). No Factory, User, Session or Snapshot schema changes are part of G6.

## Preserved Exact / Unified path

The worker analyzes an imported progression, constructs the Phase 2 match query, loads the factory and user templates once, and asks the matcher for aligned results. The engine uses each result's `continuationStartIndex`; it does not align the query again. A candidate is accepted only when the query's last chord aligns to the matched template end. Non-loop templates without a suffix are skipped. Loop templates append at most one prefix to close the current loop. Each template is one phrase, so the suffix ends at that phrase boundary.

The rhythm estimator takes known durations of matched structural events, divides query durations by template durations, and uses a median ratio. Fewer than two usable matches, or two strongly conflicting ratios, yield scale 1 and low confidence. The scale multiplies each new chord's duration. If the last query chord is OPEN and aligned to a timed template chord, the engine also returns a suggested **total** duration for that current chord. It is not a remaining playback time.

The realizer maps relative degrees into the selected key. It handles the existing core qualities, secondary dominants and leading tone chords through their global root degree, and borrowed/altered degrees. It prefers flat names in flat keys and for flat borrowed degrees, including Gb in Db major. Complex enharmonic cases and bass inversion spelling remain limited.

The engine retains template–key interpretations within the existing finite query and shortlist budgets through realization, explicit harmony constraints and melody constraints. It does not rerun alignment. Auto explores multiple keys; Forced Key restricts the query to one key. Each retained music result has one complete representative explanation, selected from actual matches; scores from different explanations are never spliced.

IntentCompletionEvaluator evaluates the realized suffix and actual input context. Template intent is a source prior. Resolve requires a tonic of the correct quality and an observed adjacent dominant, plagal or modal approach. Loop requires an actual harmonic return or a preserved catalogue cycle, including its boundaries. The recognized internal borrowed major/minor adaptation remains supported (for example C–Fm–G→Dm). Color evidence must occur in the future suffix. Develop requires a supported aligned context and a distinct multi-chord path or functional pivot. A failed Loop or Color claim does not certify Develop. A route without sufficient intent evidence is explicitly exploratory: if it passes the base score, it is accessible through the bounded More list and excluded from default recommendations.

Exact aggregation happens only after realizability and hard constraints. Music identity includes OPEN hold, normalized root/bass/pitch mask, chord quality, exact-mask realization status, color mask, full-precision durations and realization constraints normalized to the input anchor. Explanatory spelling, template ID, key, intent and cadence are excluded. Distinct bass, extension, timing and realization requirements survive. Identical music occupies one position across groups; unique source IDs and the exact generating key/window remain attached as evidence. Copying a source adds no support bonus. A repeated current chord is compared by musical semantics rather than label text.

The product has one Unified policy shared by the worker and default core context. It uses harmony-only retrieval structure (no duration, bar-position or short-approach penalty), then the established HarmonyFirst rhythm-neutral eligibility denominator. Rhythm still ranks and scales the actual suffix/OPEN hold. Strict directional extension compatibility is applied inside this same alignment; matching a simpler query to a compatible richer template never authorizes a conflicting root, third, seventh, explicit bass or altered fifth. The dev.11 realization guards still run after alignment. This is not a union of three recommendation runs.

Base eligibility retains threshold 60, with style, requested intent and source prior fixed at 0.5 and support fixed at zero. It keeps the existing rhythm-neutral weight scale; ranking retains the existing rhythm weight. Observed cadence, continuation length, actual matching and alignment penalties remain. Source quality, style, requested intent, tendency, completion tie-break and soft melody fit affect ranking after the neutral gate. Diversity affects default placement only; it cannot change qualification or delete a distinct path from More. The product retains every qualified route; its complete list has ten cards per page and a Top3 priority marker. Counts and ranks are engineering observations, not listening scores. The explanatory key confidence has zero weight in Unified matching quality: transposing a normalized route must not change its qualification or score. Equal key hypotheses and equal candidate scores use input-relative root order, preserving finite budgets across transposition. Absolute performed pitches remain in exact music identity; different sounding keys are not merged into one result.

`continuationAccess(group)` exposes retained original indices and an exploratory count for More. The editor can provide an explicit exploration action even when the default list is empty. It must not infer eligibility from a ranking threshold. The controller owns no algorithm selector; older `submitPreset` callers are migration aliases executing Unified. Sessions never persisted those experimental presets, so HCS1–5 load without a schema migration and recompute with the single policy. Explicit historical core contexts remain available only for developer comparisons.

Runtime IDs and new pin fingerprints use versioned exact music identity. Legacy references are decoded completely to compare their original music; template IDs alone cannot rebind a pin. Legacy pins cannot certify realization constraints that their old reference omitted and remain unavailable in that case. Session 5 and Snapshot 3 formats remain unchanged; only the bounded Session pin string limit rises from 8 to 16 KiB to hold complete realization references. Snapshot match key/window are recovered from the stored candidate key and alignment trace. Snapshot, Why and live provenance identify the representative match rather than the first match with the same template ID. Saved snapshots preserve their original music; recomputation is required to obtain new recommendations.

The plugin submits imports and preference changes to one worker thread. The UI polls for finished immutable results on its existing editor timer and applies them only on that UI thread. Each request has a generation number; a stale calculation is discarded when a newer import or preference request arrives. Playback transport updates only move the timeline playhead and never start analysis or recommendation. The audio processor does not read the databases or use the worker.

`recommend_cli query.json [--factory factory.db] [--user user.db] [--key C:major] [--style pop] [--intent resolve]` prints all four groups, current OPEN hold, concrete chord durations, score, key, style, cadence, support, and source IDs. `--debug` adds component scores and alignment steps. The plugin's RECOMMEND view uses a muted existing phrase segment and colored suggested suffix. It is a development view; musical judgment and Cubase interaction still need host review.

Factory V5 adds one explicitly reviewed complete pop variant to the frozen 657-entry V4 baseline. Schema 2 and all inherited IDs/payloads remain unchanged. See [the bounded family review and future inclusion rule](../data/factory-proposals/20261019-pop-variants/family-review.md). Library 5 uses a separate store directory; older repair packages cannot downgrade its active pointer, and the library-only installer requires dev.12 or newer.
